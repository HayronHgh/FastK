# 固定回測：FastK 對整體流程的實際貢獻

日期：2026-10-22。已實作、已跑完。新增的是外部回測工具與證據，FastK 核心、native 接口與現有五個 adapters 維持原樣。

以同一個 Python／NumPy 回測，讀相同的 2024 BTCUSDT／ETHUSDT 一分鐘資料，共 1,054,080 筆。只切換 FastK、Arrow IPC、Parquet、DuckDB、SQLite；另有明確標示的預載記憶體對照。這次直接看策略、撮合與資料讀取加在一起需要多久。

## 結論先看整體貢獻

逐月載入時，FastK 的全年資料準備約 22–24 ms；Arrow 約 37–40 ms。這個差距不會等比例放大成回測加速：

- RSI：FastK 539.07 ms、Arrow 553.53 ms，總時間中位數少 2.61%。RSI 遞迴與其他共同工作佔大部分時間。
- SMA：142.11 對 155.82 ms，少 8.80%；同時比 Parquet／DuckDB／SQLite 的 261.52／454.39／1,224.05 ms 低。
- 動能：331.20 對 333.85 ms，差 0.79%，相較五程序波動接近平手，不能宣稱穩定領先。

整年一次載入時，三案例 FastK 比 Arrow 的總時間中位數分別少 7.08%、19.73%、8.11%。這是這組真實資料、輸出格式與現有 adapters 的結果，不是所有回測都會有的固定倍數。

逐月 FastK 載入佔總時間約 4.44%／16.12%／6.79%。即使理想預讀完全隱藏資料準備，單就這個成本最多只剩這個量級可省，還沒扣背景執行／同步的成本。這份 workload 不支持為追求命中率而無限加大快取；後續持續通道應以端到端等待與已知重複需求驗證。

FastK 的實用貢獻在於資料準備延遲較低，且本次程序記憶體較低。CPU 工作越多，資料層差距越容易被稀釋。不能把載入倍數當成整體倍數，也不能把 Python 撮合／JSON 交易摘要的耗時算到儲存引擎上。

## 固定模型與流程

三案例均套用兩個標的，各以 50,000 初始資金獨立 long/flat 操作，不跨帳戶再平衡。RSI(14) <=30 買、>=70 賣，區間內保留目標；SMA20>SMA60 持有、否則空手，暖機 60 根；60 根動能以當前收盤是否高於 60 根前收盤決定持有。RSI 使用 Wilder 遞迴，14 個變動起始平均，平盤 RSI=50。計算定義參考 [TA-Lib RSI 原始碼](https://github.com/TA-Lib/ta-lib/blob/main/src/ta_func/ta_RSI.c)，沒有引入該套件。

收盤產生訊號，在下一根可用 K 線開盤成交；每邊手續費 10 bps、逆向滑價 1 bp，允許零碎數量。跨月保留指標、待執行目標、持倉與現金。期末以最後收盤估值，不憑最後訊號虛構一次成交。模型沒有槓桿、空單、流動性限制或 funding；資金計算是共同 float64，儲存輸入維持完整 int64。

逐月：開接口 → 讀兩個標的 → 關接口 → 運算 → 釋放輸入，重複十二次。整年一次：同一流程，只開一次、讀兩份全年資料。兩種切法完整交易與資金曲線必須一致。資料缺口不補值，lookback 計可用 bars；此簡易組合模型要求標的時間戳對齊，不對不齊的資料默默 forward-fill。

固定成本下三個未調參的分鐘策略皆大幅虧損，完整收益與費用表保留。它們用於驗證固定工作量和後端等價，不以收益挑選設定。

## 公平性、量測與反證

每個正式設定有五個獨立程序，六個資料來源 × 三策略 × 兩生命週期，共 180 次完整回測。每輪順序固定種子隨機，所有引擎及數值函式庫工作執行緒額度為 1，不同後端不同時競跑。

計時從應用初始化開始，含 caller manifest 讀取、排程與狀態、開讀關、指標、撮合、收盤權益／回撤、資金曲線摘要、交易摘要與資源釋放。套件匯入及 Python 程序啟動不在這個 resident-process 應用計時內。完整曲線摘要在共同 compute 階段，交易排序／摘要與 engine 清理在 finalize；各階段原始數值均保留。

正式執行前，來源 24 個 bars 檔 SHA256 已核對，五後端共 130 個查詢結果逐欄完整 packed bytes 與 canonical 資料一致，且資料在 close 後仍可用。180 個正式結果再以完整曲線、交易摘要、費用、最終持倉與權益核對，跨後端、輪次與切批全部一致。

首輪 `real-year` 發現 Arrow 第一次 query 還做了 `pyarrow.dataset` 延遲匯入，其他後端已預先匯入依賴，造成數十 ms 偏差。因此保留首輪並排除排名，修正 bootstrap 後全部五輪重跑；本文件只用 `real-year-verified`。初始 measured worker bytes、SHA 與修正原因均存入證據，不把匯入成本包裝成 FastK 優勢。

預驗證會暖 OS cache，且沒有驅逐 OS cache／實體磁碟 IO 證據，所以本輪是每次 fresh interface 的開讀關與回測，不是 cold-disk 實驗。記憶體對照先載入 canonical 資料，預載及該資料最終卸載不在其應用計時內；它只提供 resident-data 成本參考，不能拿來證明持久化效能或最低 RSS。

五後端都回傳同一份 packed readonly NumPy layout。SQLite 含 `fetchall`→NumPy 及既有 `Path.resolve()` 開啟成本；DuckDB 用 `fetchnumpy`；Arrow 含欄轉列組裝；Parquet 含解壓與查詢。因此是現有 Python 交付路徑的比較，不直接歸因成底層算法本身差距。寫入、建庫、修訂、可靠性與磁碟容量不在本輪量測範圍。

Windows GNU、Python 3.12.14、NumPy 2.3.5、PyArrow 26.0.0、DuckDB 1.5.6。實測 native SHA256：`69781ff8ebbcdcab364642b2b3aaff0e3ca76aad51fa7693281dc297eaa9d4b1`。原生 Linux／MSVC 留待有環境後驗證。
